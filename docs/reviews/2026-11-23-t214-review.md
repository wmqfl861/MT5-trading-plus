### 1.3 重点审查的六个问题

**问题 1：判据是否恰当**

与 §3.2 第 3 条逐项对照见 §1.1。阈值本身（600 秒、3600 秒、10 GiB）与计划一致，立即判的两项（磁盘、日报）也与计划一致。问题出在下面几处。

- **(a) "角色消失时心跳年龄已超过 600 秒，第一次检查就判生产级"——成立，没有找到误判。**
  - 已验证：旧启动器退出、登记还没更新时，心跳 100 秒 → `role_missing:risk`，非生产级；心跳 700 秒 → `role_missing:risk`，生产级。
  - 已验证：登记已经指向新启动器（启动 30 秒）、心跳文件还是旧进程留下的。心跳 100 秒 → 没有发现；心跳 700 秒 → `heartbeat_stale:risk`，生产级。这时角色确实已经停了 11 分多钟，超过"10 分钟没有被拉起"，判生产级是对的。supervisor 正常重启在 3 分钟内完成，新进程马上写心跳，撞上"心跳超过 600 秒"就说明角色确实停了那么久。
  - 读码结论：supervisor 重启角色时先启动进程、后改写登记（`live_supervisor.py:436-443`），中间有一个很短的窗口登记还指着旧 PID；正常重启里旧心跳不超过 3 分钟，不会触发。
  - 两处不准确：这种情况报出来的代码是 `heartbeat_stale` 而不是"角色消失"；消息里的时长是 0 分钟（S-8）。
- **(b) 日报"缺失"——误报存在，而且比预想的大得多。**
  - 推演（读码结论）：
    1. 日报任务在本机 05:57 运行，本机时区是 UTC+8（已验证），即 UTC 21:57。它用 `--date yesterday`，脚本里 `yesterday` 是 **UTC 日期减一天**（`scripts/live_daily_report.py:83-84`）。所以第 X 天的日报在 **X+1 天的 21:57 UTC** 才生成。

**问题 2：通知器**

- 只在有生产级问题时发：已验证。没有生产级问题时 `notify()` 返回 `none`，发送器不被调用。
- 每小时重复发：已验证。问题还在，每次运行都发一条，内容只有时长不同（停机文件放着不动，连续四小时发了 4 条；日报误报场景 48 小时 44 条）。计划写的是"当小时通知"，可以理解成"当小时内通知到"，没有要求每小时重发。没有去重的后果：风控停机锁存到下一个 UTC 日、人工 pause、计划性停机，都会变成每天二十来条同样的消息。O23-8 要解决的就是"告警没人接"，重发会让人更快学会忽略它。建议去重（S-7）。
- 消息内容：已验证，只有问题代码、角色、时长，不含路径、账号、服务器名。两处要改：首次发现时时长恒为 0 分钟（S-8）；只有"MT5 Demo"一个标识，多套部署并存时分不清是哪一套（G-9）。
- 接口够不够以后加渠道：`SENDERS` 是"渠道名 → 函数"的表，检查逻辑（`observe`、`evaluate`）不碰通知，加一个渠道只需要加一个函数和一条表项，这部分够用。不够的地方：发送器的签名是 `(target, message)`，带不了渠道自己的配置（邮件的服务器和凭据、机器人的 token 和会话 id），U10 的三类里只有即时通讯的 webhook 能直接套；"通用 webhook"的载荷固定是 `{"text": …}`，只对接受这个格式的服务成立（G-9）。
- `target` 的处理（已验证，传输层打桩，没有发真实请求）：
  - `target` 是一段 shell 文本：不经过任何 shell。标准库把它解析不出来的地址报成 `URLError`，结果是退出码 2、`{"ok": null, "error": "URLError"}`；配置内容没有回显。
  - `channel` 是 `webhook`、`target` 指向内网地址：照发。回环地址、内网地址、链路本地元数据地址、`ftp:`、`file:`、`https:` 全都进了对应的标准库处理器，发的是 POST。
  - 对方回 302 指向内网地址：会跟过去，第二个请求是 GET，不带消息体。
  - 风险判断：配置文件只在本机、由运维写，所以要利用这些得先改得了本机配置；消息本身不敏感，响应内容不输出。风险低，但应该收紧（S-12）。
- 发不出去的时候：退出码 2，问题清单不输出，"有生产级问题"的结论丢了（S-1）。状态文件在发送之前已经写好，时长不会丢。

## 3. 发现清单

位置没有写文件名的，都指 `scripts/ops/liveness_check.py`。

### 阻断

**B-1. "日报缺失"的判定与日报任务的实际时刻不符，健康现场每天约 22 次误报。** `:119-121`、`:159-160`；夹具 `tests/test_t214_liveness_check.py:71-72`。

- 事实与推演见 §1.3 问题 1(b)，实测见 §2.D-1。
- 影响：通知器装上去的第一天起，每天 00:00–21:57 UTC 每小时一条"日报缺失"。真实的日报缺失（O23-9 那种连续多日失败）混在里面分辨不出来；用户很快就会不再看这些消息。
- 改法：按"已经到期的最近一份日报"来判。第 X 天的日报到 X+1 天 21:57 UTC 之后才应当存在，T213 的重试再留出宽限，所以 UTC 22:30 之前要求前天的，之后要求昨天的。这个时刻不要依赖主机时区，做成参数或者从部署记录读。补一条按真实时刻表取几个钟点（00:00、12:00、21:56、21:58、23:59 UTC）的测试，这条测试在 `f239862` 上必须失败。

### 应改

标 ★ 的在合入前改，其余在装计划任务之前改。

**★S-1. 通知发不出时丢掉"有生产级问题"的结论。** `:225-228`。`notify()` 和检查、写状态在同一个 `try` 里，发送器的异常进了同一个 `except`：退出码 2，输出里没有 `findings`。已验证（§2.B(4)）。这台机器到经纪商的网络本来就不稳（O23-7），这条路径会被走到。改法：发送单独捕获；失败时照常输出问题清单，退出码保持 3，`notified` 记成 `failed` 并带上异常类名。

**★S-2. 状态文件写不了时同样丢结论，而且不发通知。** `:221-224`。已验证（E1、E1b）。盘写满正是它该报告的情形，这时它只留下一行 `OSError`。改法同上：写状态失败不阻断通知和输出，单独记 `state_error`。

**★S-3. 退出码 2 过载，自身出错只报异常类名。** `:226-228`。已验证（§1.3 问题 3）。改法：输出加固定的 `step` 字段；有生产级问题时退出码保持 3；参数错误另行处理或至少写明。

**★S-4. 输出的一行 JSON 会带出 halt、pause 的 `reason` 原文，里面可能有路径和账号。** `:106`、`:111`。已验证（§2.B(6)）。和 `:226` 的注释"the output must not leak paths"是矛盾的；提交说明里"输出不含本机路径"只在没有 halt 的现场成立。仓库的卫生扫描只认用户目录下的路径和"账号"等关键词，生产根目录迁到工作区之外以后，这行输出一旦被贴进 phase-f-log，扫描发现不了。改法：只保留原因代码（第一个冒号之前的部分），或者不带 `reason`；补一条测试。

**★S-5. 存在但读不出、或者不是对象的 `halt.json` 和 `pause-*.json` 被当成没有。** `:104-105`、`:108-112`。已验证（E10）。生产对这些文件是 fail-closed。一个空的 `halt.json` 会让系统停机，检查器却什么都不报。读不出心跳和 `supervisor-state.json` 都会报，只有这两类不报。改法：文件存在就算有问题，读不出时 `age_s` 记 `null`。

**S-6. 时间戳在未来被算成新鲜；不带时区的时间戳被当成本地时间。** `:79`。已验证（§2.B(2)）。生产的约定是不带时区即 UTC，`age < 0` 判不健康。改法：负的年龄不要截成 0，记成 `null` 或者原样保留；不带时区的按 UTC 处理。

**S-7. 问题还在就每小时重发同一条消息。** `:188-203`，状态文件不记"已经通知过"。已验证（§2.B(4)）。改法需要主会话或用户定策略。建议：进入生产级的时候发一次；生产级问题的集合变了再发一次；之后每 6 小时提醒一次。

**S-8. 首次发现时消息里的时长恒为 0 分钟。** `:171`。`format_message` 用的是检查器自己的时钟，判定生产级时用的却是"自己的时钟和文件时间取大"。已验证（E3）：停机两小时的 halt，消息是 `halt(0分)`。改法：用判定时的那个有效时长，并且用"小时""天"来显示长的时长。

**S-9. 登记项的字段缺失或类型不对时，记成"角色消失"或者直接崩溃。** `:95-99`、`:64-66`。已验证（§2.B(1)、(5)）。缺 `started_utc`、`started_utc` 不是时间，都是"没法判断"，不是"不在"；`pid` 不是整数时 `ArgumentError` 不在捕获列表里，`instances` 数组里有非对象项时 `AttributeError` 也没有被接住。崩溃之后每个小时都是退出码 2，没有通知。改法：判断不了的记 `launcher_alive: null`，单独一个非生产级的发现；登记表里有不认识的项时报 `registry_unreadable`。

**S-10. 状态文件是合法 JSON 但形状不对时，每次运行都是退出码 2，状态文件也不会被重写。** `:161`、`:164`、`:220`。已验证（§2.B(3)）。改法：读出来不是对象、或者 `since` 不是可用的时间，就当空状态重新起算。

**S-11. 没有渠道时是静默的。** `:194-198`。配置文件丢了、坏了、缺字段，结果都是 `no_channel`，退出码仍是 3，不发通知，也没有别的信号。已验证。T215 把生产迁到新目录时，`*.local.json` 没跟着过去就会这样。改法：`no_channel` 和 `unsupported_channel` 用一个和"已发出"不同的退出码，或者由调度日检核对（§4）。

**S-12. webhook 渠道不限制协议、主机和重定向。** `:175-182`。已验证（§2.B(4)）。风险低，见 §1.3 问题 2。改法：只允许 `https`；不允许跟随跳到别的主机的重定向；响应不要整个读进来。

**S-13. `supervisor_stale` 名不副实。** `:103`、`:148-149`。supervisor 拒绝时每分钟都在检查，但它在拒绝路径上写的状态文件没有 `last_checked`（`live_supervisor.py:486`），重启路径上也没有（`:412`）。检查器把它记成"supervisor 不检查"。11-21 那 684 分钟就是这个形态，报警能出来，但会把排障的人引向"任务没在跑"。已验证（§2.B(1)）。改法：结合 `halt.json` 的 `owner` 是 `supervisor`、`reason` 是 `supervisor_refused`，报成 `supervisor_refused`。

- **G-1.** supervisor 新鲜度的发现阈值是 120 秒（`:24`、`:148`），计划写的是 3 分钟。不影响生产级判定，写明理由或改成 180 秒。

### 5. N-8 的独立模型

规则是：某一天的日报，只在登记表里最早的 `started_utc` 早于那一天的 00:00 UTC 时才要求。模型里另外记录了事实：这个数据目录什么时候建立、哪几个角色什么时候被重启（supervisor 重启角色时会改写登记里的 `started_utc`）、哪几次日报任务失败。下表里除注明外，日报任务一次都没有成功过；检查整点跑。

| 场景 | 误报 | 第一条通知 | 日报确实没出来、检查器没有报的 |
| --- | --- | --- | --- |
| 新目录，D 日 10:00 部署，日报正常（144 次检查） | 无 | 没有发现 | 无 |
| 新目录，D 日 10:00 部署 | 无 | D+2 日 23:00，部署之后 61 小时 | D−1、D 两天的日报 |
| 新目录，D 日 00:30 部署 | 无 | D+2 日 23:00，部署之后 70.5 小时 | D−1、D 两天的日报 |
| 已跑 20 天，R 日 10:00 四个角色全部重启，日报正常 | 无 | 没有发现 | 无 |
| 同上，日报从 R 日 21:57 那一次起一直失败 | 无 | R+2 日 23:00，第一次失败之后 49 小时 | R−1、R 两天的日报 |
| 同上，只有 R 日 21:57 那一次失败 | 无 | 没有 | R−1 那一天的日报永远不报 |
| 只重启一个角色，R 日 21:57 那一次失败 | 无 | R 日 23:00，晚了半小时 | 无 |
| 不重启（对照），R 日 21:57 那一次失败 | 无 | R 日 23:00 | 无 |
| 新目录，登记里的 `started_utc` 被写成 30 天前 | 有：部署当天 10:00 到 22:00 的 13 次检查都报，发了一条通知和一条已恢复 | — | — |
| 登记表是空的 | — | 没有，也没有任何发现，`ok: true` | 全部 |
| 登记表读不出、不存在 | — | 没有（有 `registry_unreadable`） | 全部 |
| 登记里的 `started_utc` 被写成一年之后，探针被设定成"存活" | — | 没有，也没有任何发现 | 全部 |

怎么读：

- **想要的效果有了**：新目录部署的当天不再报缺，全量重启的当天也不会。
- **代价比说明里写的大。** 实现方的说明是"那一天的日报就不要求，第二天起恢复"，主会话按这个确认了。实测是两天：四个角色在 R 日全部重启之后，R−1 的日报（R 日 22:30 到期）和 R 的日报（R+1 日 22:30 到期）都不要求，第一条通知要等 R+1 的日报，也就是 R+2 日 22:30 之后。只失败一次的话，那一天永远不会报。全新部署也是两天，从部署到第一条通知的时间看部署的时刻：23:00 UTC 部署是 48 小时，10:00 是 61 小时，00:30 是 70.5 小时。
- **空窗落在什么时候。** 四个角色同一天全部重启，就是每一次重新部署和每一次整机重启之后。全新目录里日报任务没装好、装错了目录，正是这个时候最可能出的事，检查器要等到第三天才报。施工计划 §3.2 第 3 条写的是日报缺失"当小时通知"。
- **登记表不可信的时候。** `started_utc` 被改早，N-8 之前的误报就回来；被改晚，日报检查跟着关掉。后者有别的信号兜着：真实的进程探针对不上登记的启动时刻，会报四个角色消失。空登记表则什么发现都没有。
- **有兜底，但不是检查器。** T213 自己的失败告警和调度日检对日报的检查都还在，起算前提第 7 条也要求日报连续三天成功。所以这不至于让问题无人知道，但"日报缺失由小时级检查器当小时通知"这一条，在部署和重启之后两天多是不成立的。

**建议的改法**（供主会话定，改动很小，已验证）：把"那个 UTC 日开始之前部署已经在跑"换成"那份日报生成的时候部署已经在跑"，也就是 `started_utc` 早于次日 21:57 UTC 才要求。评审把 `_owed` 换成这一条，其余不动，跑同一组场景：

| 场景 | 现在的规则 | 建议的规则 |
| --- | --- | --- |
| 新目录 D 日 10:00 部署，日报正常 | 没有发现 | 没有发现 |
| 新目录 D 日 10:00 部署，日报一直不工作 | 两天没报；D+2 日 23:00 才报 | 当天没有漏报；D 日 23:00 就报 |
