## 1. 结论

1. **11-23 没有起算，窗口仍是 0/10。**

   - 到 11-22 13:16 的日检为止一直是 0 进程，原定的 11-22 部署没有执行。

   - STATUS 停在 11-20，仍写着"新第 1 天 11-23"。本轮改写，并且不再预定日期（D108）。
2. **11-23 的两个提交（O23-1）不能作为窗口的部署候选。** 没有测试，没有入库的评审记录，提交说明有两处与改动不符。它对"启动器下挂一个系统 conhost"这一种形态有效，另外两种 conhost 形态仍然拒绝。更要紧的是，11-21 的根因到现在没有取证，这次修的是猜测的原因（O23-1、O23-6）。
3. **supervisor 的身份校验还有三个与 conhost 无关的缺陷**，前两个各自都能造成"每分钟一条 mismatch、不会自愈"：
   - 已退出的启动器的 PID 被无关进程占用（O23-2）；

7. **按现行口径和现有环境，A5 一次通过的概率很低**（§4）。本轮不建议放宽口径，先修原因。
8. **A5 不在关键路径上，研究线才在**（§5）。十多个候选零通过；F3、F1 的数据扩充排在 A5 之后，而 A5 已经滑了四周；D107 安排"现在就做"的两项纸面工作没有产出。本轮把研究线和 A5 解耦（D117）。

## 3. 发现

### O23-1 [High] 两个 conhost 提交未经验证就标为"根治"

- **事实**：
  - `70cd7eb..ded9407` 只改了 `scripts/live_supervisor.py`，没有改任何测试（P23-5）。`docs/reviews/` 里没有对应的评审记录。
  - `4609be1` 的说明写了三项："跳过 conhost""canonical 改用 pathlib 归一化""`_argv_matches` 兜底"。diff 里没有对 `_argv_matches` 的任何改动；`canonical` 的新写法对正常路径与原实现结果相同（`Path.resolve` 内部就是 `os.path.realpath`）。实际只有第一项。
  - D102 把树内修复（T208）排在 A5 之后，并要求在真实 Windows 上测试。这次提前做了，但没有测试。
- **效果**：
  - 启动器下挂一个系统 conhost 叶子：通过（P23-3a）。
  - 有任何进程的 `parent_pid` 等于 conhost 的 PID，conhost 就不算叶子，仍然拒绝。这个判断没有按创建时间排除陈旧的父链接，而同一函数里遍历子进程时是排除的（P23-3b）。
  - 启动器已退出、conhost 还没退出的瞬间，root 缺失分支不认识 conhost，报"missing launcher with surviving/duplicate worker"（P23-3c）。`terminate_verified_tree` 结束进程之后马上复核，正落在这个时序上；撞上的话本轮重启中断，下一分钟才补上。
  - `verified_tree` 里现在读环境变量、访问文件系统。文件头写明"OS 动作全部放在 WindowsProcesses，供离线状态机测试"，这次改动破坏了这一点，所以在非 Windows 上写不出能通过的单元测试。
- **与 11-21 的关系**：11-20 日检记录四棵树"conhost 全 0"（`host.py` 把启动标志改成了 0）。按日检的记录，01:24 第一条拒绝之前没有任何告警，也就没有 supervisor 发起的重启；在 `host.py` 之下 conhost 不会凭空出现。conhost 不像是那次的原因，最终以取证为准。
- **处置（D110、D118）**：这两个提交留在 main（不改写历史），不作为部署候选。并入 T211：补测试、改成纯逻辑、修掉 3b 和 3c、独立审核。

### O23-2 [High] 已退出启动器的 PID 被复用，会被判成"参数不符"并一直拒绝

- **事实**：`verified_tree` 先取 `table[登记的 PID]`，只要这个 PID 上有进程，就进 `_identity`：先比参数（不符即报 `process script/arguments mismatch`），后比创建时间。登记的启动器已经退出、PID 被别的程序占用时，走的是"参数不符 → 拒绝"，不是"启动器缺失 → 重启"。
- **实况**：11-19 恢复单的只读实测里就有这个形态——risk 的启动器已退出，同一个 PID 上是一个 11-18 启动的系统进程。恢复单指出"PID 复用会独立造成拒绝"，之后没有立任务。
- **为什么常见**：Windows 回收 PID 很快。supervisor 自己每分钟就要起近十个短命进程（包装器、powershell、三次 git）。占用者如果是常驻进程，拒绝就一直持续到它退出。
- **复现**：P23-1。
- **处置（T211）**：PID 上的进程创建时间与登记不符、参数也不符，判为启动器缺失，再做孤儿扫描。参数相符而创建时间不符（疑似登记外的重复 worker）仍然拒绝，现有测试 `pid_reuse` 保持。

### O23-3 [High] 终端被 worker 拉起后成为它的子进程，supervisor 从此拒绝（O22-7 升级）

- **事实**：
  - 终端进程不在时，`MT5Connection._attempt_reconnect` 调 `mt5.initialize(terminal_path, …)`。真实的 MetaTrader5 包这时会启动 `terminal64.exe`，父进程就是调用它的 worker。第二十二轮 O22-7 已经在生产上见到。
  - `verified_tree` 要求每个后代都通过 `_identity`，终端过不了，报的也是 `process script/arguments mismatch`。终端活多久，拒绝就持续多久。
  - 启动时的 `connect()`、日报任务的 `gw.connect()` 走同一条路，同样会拉起终端。
- **与 11-21 的吻合点**：按日检的记录，首条 mismatch 之前没有任何告警；当晚 902610 有 5 次 10021 拒单，是终端楔死的特征，夜里终端重启过的可能性不小；风暴一直持续到所有进程消失。这是推断，要靠 O23-6 的取证确认。
- **复现**：P23-2。
- **处置（D111）**：T209 提前到本次候选，范围见施工计划 §2。

### O23-4 [High] 测试里的进程形态和生产不一样

- **事实**：
  - 生产有两条启动路径：`demo_run.ps1` 的 `Start-Process -WindowStyle Hidden`，以及 `WindowsProcesses.launch()` 的 `CREATE_NO_WINDOW`。两条都会让新进程带一个 conhost 子进程。
  - `tests/test_t110_supervisor.py` 里三个真实 Windows 测试都是测试自己用 `subprocess.Popen` 起假角色，再交给 `verified_tree`。这些测试在 CI 上一直通过，说明那里的子进程没有带 conhost（推断：测试进程自己有控制台，子进程继承它）。
  - 没有任何测试调用 `launch()` 之后再做身份校验。`tests/` 全目录没有"conhost"一词（P23-5）。
- **后果**：supervisor 在生产上遇到的三类拒绝——conhost（11-17）、PID 复用（11-19 实测）、11-21 的未知后代——都是测试里没有的进程形态。CI 一直是绿的。
- **处置（T211）**：加两条在 CI（windows-latest）上跑的端到端测试，分别走两条生产启动路径；两条都必须在 `70cd7eb` 上失败。把失效模式列成表，每一行对应一个参数化测试。

### O23-5 [High] 部署核验的 git 超时会写 halt，并让窗口失败

- **事实**：`verify_deployment` 每分钟跑三条 git 命令（其中一条是 `git status --porcelain --untracked-files=all`），各 15 秒超时。超时抛 `TimeoutExpired`，被最外层捕获后写 `halt.json`（`supervisor_refused`）并发 `SUPERVISOR_REFUSED`。正式检查把 `SUPERVISOR_REFUSED` 归为异常类，窗口内一条就判失败。
- **实况**：11-20 03:40 UTC 发生过一次，之后自愈。git 为什么会卡住没有查，日检建议交本轮审核。
- **量级**：一个窗口大约两万次核验、六万次 git 调用，全部不超时才算过。
- **复现**：P23-4。
- **处置（D115、T212）**：把"无法判定"和"拒绝"分开。这是健壮性修复，不改变任何验收口径：真正的身份或部署不符照旧拒绝、照旧判异常。
