### 1.1 安全立场

- **被豁免的 conhost 不进终止清单。已验证。** `visit()` 先把 PID 放进 `seen`，再判 `_console_leaf`，为真就 `return`，在 `result.append(item)` 之前（`scripts/live_supervisor.py:262–264`、`:271`）；`_require_launcher_gone` 只抛异常，不返回进程。行 2 的测试断言返回值是 `[101, 100]`；两条端到端测试断言 conhost 的 PID 不在树里。
- **"系统 conhost"只凭完整路径。已验证。** `_same_path(executable, ntpath.join(system_root, "System32", "conhost.exe"))`（`:212–214`）：`ntpath.normcase(ntpath.normpath())` 归一后做字符串相等，再加"叶子"条件。同名的 `SysWOW64\conhost.exe`、兄弟目录下的 `conhost.exe`、只有文件名、带尾点的写法，在新代码上一律拒绝。

- **conhost 下有创建时间不早于它的子进程时仍然拒绝。已验证。** `:215–217` 判为非叶子，随后走 `_identity` 被拒绝；子进程晚于、等于 conhost 两种情况都拒绝。
- **不在系统目录的同名映像仍然拒绝。已验证。** 行 5。

### 1.3 "判定改成纯逻辑"

- **conhost 判定本身是纯的。已验证。** 把 `canonical` 和 `os.path.realpath` 换成会抛异常的函数，`_console_leaf` 照样返回 True；`_decide_tree` 不调用 `os.environ.get`。
- **`os_system_root()` 是唯一读 `SystemRoot` 的地方。读码结论。** 全文件只有这一处 `os.environ`。
- **偏离计划原文的两点。已验证。** 其一，公开入口 `verified_tree` 在没传根目录时读环境变量，而生产的三个调用点（`:407`、`:420`、`:423`）都不传，所以字面上的"`verified_tree` 里不读环境变量"没有做到。其二，`_decide_tree` 经 `_identity` 和 `_argv_matches` 调 `canonical()`（`os.path.realpath`），树里有 worker 时就访问文件系统，docstring 里的 "no filesystem" 和提交说明里的"纯函数"不准确（S2）。这部分是 `70cd7eb` 就有的 worker 路径归一化，不是本次引入的。
- **为什么接受。** 计划允许因签名变化改探针里的调用，不允许改判定条件。实现者的做法让 P22-4、P23-3 原样运行、判定条件不变，并且翻转为预期结果（§2.5）；判定对系统根目录是纯函数，表里的每一行都能在合成表上、在任何平台测。另一种做法（必须显式传参，再改探针调用）同样合规，安全性上没有差别。接受的前提是把偏离写明，本记录即为此。
- **`canonical()` 的边界划分合理。** conhost 的映像路径是系统报告的规范绝对路径，字符串比较足够，也不依赖被比较的文件是否存在；worker 的 `argv[0]` 与 `executable` 要经 realpath 归一（venv 重定向器形态），这是既有逻辑，与 conhost 判定无关。

### 2.3 C 步骤：两条端到端测试

| 启动路径 | 启动器下的进程（相对启动器的创建时间） | `verified_tree`（环境里的根目录） | `verified_tree`（根目录传 None） | 终止后复核 |
| --- | --- | --- | --- | --- |
| `WindowsProcesses.launch()` | `conhost.exe` +5 ms；`python.exe` worker +36 ms | `[worker, 启动器]` | 拒绝 `process script/arguments mismatch` | `[]` |
| `Start-Process -WindowStyle Hidden` | `conhost.exe` +23 ms；`python.exe` worker +99 ms | `[worker, 启动器]` | 拒绝，同上 | `[]` |

conhost 的创建时间晚于启动器，所以它会被 `visit` 遍历到，不会被当成陈旧父链接跳过；根目录未知时同一张表被拒绝，说明让测试通过的是 conhost 豁免，不是别的分支。另外，这两条测试在 `70cd7eb` 上失败（§2.4）。

`console_hosts` 只按文件名匹配，不要求是系统 conhost；但换成一个非系统的 conhost，`verified_tree` 会拒绝，测试失败而不会空过。

### 1. 机理（指到行）

生产上的树是两层：启动器（venv 的 `python.exe`，只做一件事——等它的子进程；用 `demo_run.ps1` 启动时它下面还有一个
conhost，不在终止清单里）和解释器 worker。`_decide_tree`
（`scripts/live_supervisor.py:341-379`）按"子先父后"返回（`:374`），所以结束一棵树时 `terminate_verified_tree`（`:522-536`）
先 `terminate(worker)`，紧接着 `terminate(launcher)`（`:530-531`）。

- worker 一死，启动器等待的那次等待就返回，它随即调 `ExitProcess` 自行退出。它**完全退出**是在 `terminate(worker)` 返回之后
  4.3–13.6 毫秒（8 轮）；**开始退出**早得多，见第 2 节的表，0.1–0.2 毫秒时已经在退出途中。
- `WindowsProcesses.terminate`（`:833-858`）打开句柄、核对创建时间之后直接调 `TerminateProcess`（`:853-854`），没有先看目标
  是不是已经在退出。目标在退出途中、或者已经退完而进程对象还在，`TerminateProcess` 都返回 FALSE，脚本抛
  `RuntimeError("termination failed")`（已退完的那一种量到 `GetLastError` 是 5；退出途中的那一种只量到返回 FALSE）。
  进程对象也不在了的时候，`OpenProcess` 失败（PID 已不存在，错误 87），抛的是另一句
  `RuntimeError("cannot acquire process handle")`（`:842-844`）。
- 两次 `terminate` 之间生产代码自己要走不到 0.15 毫秒（量到的），第二次调用内部发出 `TerminateProcess` 之前还有几十微秒。
  **每结束一个活着的角色都是一场只差百微秒的赛跑**：这一侧先发出 `TerminateProcess(launcher)` 就成功，启动器先走进退出就失败。
  这里没有超时。负载给两边都加抖动——启动器那一侧同样要等 CPU，所以满载并没有让它更容易出现（第 3 节）。

### 2. 窗口表

做法：和测试一样用 `Start-Process -WindowStyle Hidden` 拉起一个只休眠的假角色（树是启动器、它的 conhost、worker），用生产调用结束
worker，等一段延迟，只读地查启动器的状态，再用生产调用结束启动器（2026-11-24T04:44:20Z 至 04:45:18Z，每个延迟两轮）。

| 结束 worker 之后等多久 | 发出结束启动器之前启动器的状态 | `terminate(launcher)` |
| --- | --- | --- |
| 0、0.05 毫秒 | 运行中（退出码 259） | 成功（两轮都是） |
| 0.1 毫秒 | 运行中 | 一轮成功，一轮 `termination failed` |
| 0.2–4 毫秒 | 运行中，退出码已是 75 或仍是 259：退出途中 | `termination failed` |
| 8–100 毫秒 | 已退出（75），进程对象还在 | `termination failed` |
| 300–1000 毫秒 | 进程对象已不在（错误 87）；600 毫秒那一轮还在 | `cannot acquire process handle`；那一轮 `termination failed` |

另一次核对：两次调用之间人为停 0.1 秒，得到 `termination failed`（+0.10 秒）；等进程对象消失后再调用，得到
`cannot acquire process handle`（+0.85 秒）。一个普通的子进程退完而句柄还开着时，`OpenProcess` 成功、`TerminateProcess` 返回 FALSE、
错误码 5；最后一个句柄关掉后 `OpenProcess` 失败、错误码 87。

### 9. C3：日志年龄的负值，加 2 秒容差

**实现子代理代拟，待主会话核对。不是评审结论。** 主会话在观察运行里查到两次多余的重启（原因码都是

本小节记这个提交做了什么、自测看到的输出。时刻取自系统时钟。

**机理。** 检查式是先 `stat` 角色的日志、再读时钟，`age` 是读到的时刻减去日志的最后写入时间。写完一个文件之后，它的最后
写入时间可以比紧随其后读到的时钟略微超前，于是 `age` 是一个很小的负数。重跑了主会话的两个探针（在仓库之外，不入库），

| --- | --- |
| `datetime.now()` 的步长：本机，Python 3.12.10，0.4 秒里读了 32693 次 | 只有 395 个不同的值，步长集中在 990–1004 微秒 |
| 主会话的 `clock_probe.py`，2 万次写入 | 13975 次文件的写入时间早于随后的 `datetime.now()`，最大 0.001 毫秒；心跳"来自未来"0 次 |
| 主会话的 `race_probe.py`，5 秒 | 7291 次检查里 14 次 `age < 0`，最坏 -0.001 毫秒；心跳"来自未来"0 次 |
