## 3. 发现

### O22-1 [High] 运行器断线告警被正式检查判为异常，新窗口第 1 天就会失败

- **事实**：
  - `src/mt5live/executor.py` 在三种情况下写 `BROKER_UNAVAILABLE`：
    - 券商持仓查询失败；
    - 挂单查询失败；
    - 下单前 `NotConnectedError`。
  - 三种都是 T201 设计好的 fail-closed：本轮不开仓，下一根 K 线重试，进程不退出。
  - `scripts/demo_check.py` 却把 `BROKER_UNAVAILABLE` 放在 `FORMAL_ANOMALY_ALERTS` 里，窗口内一条就判"窗口内异常"（返回 1）。
- **实况**：
  - 11-17 12:36 一次断线就产生 4 条；
  - 11-18 13:16 到 11-19 13:16 共 22 条，对应的都是 5 秒以内的闪断。
- **为什么以前没暴露**：PaperSoak 用纸面券商，不查真实持仓，不会写这条告警。正式窗口是第一次在 Demo 模式下长期运行 T201。
- **复现**：P22-1。合成窗口第 2 天加一条运行器断线告警，返回 1，判"窗口内异常"。
- **处置（T210(a)，D105）**：
  - 消息里的异常类型是 `NotConnectedError`、`PreSendUnavailableError` 或 `DataUnavailableError` 的，改为记录类：逐日计数、写进 A5 材料，不另计降级秒数（同一断线的时长已由风控/对账的 `DISCONNECTED` 段计入）。
  - 其他异常类型照旧判异常。

### O22-2 [High] 非交易日的长断线也判窗口失败

- **事实**：
  - T141 的 rc=78 退出告警一律按异常处理；
  - 1800 秒/日的降级上限按窗口内**全部自然日**计算，周末和节假日也算（`required_calendar_days`）。
- **实况**：11-15（周日）有两段断线，分别 1523 秒和 1554 秒。落在窗口内的话，两条规则都会判失败。
- **为什么不合理**：周末黄金休市，持仓不会变，止损止盈挂在服务器上。这时风控看不到账户，没有任何交易后果；判失败测的是经纪商周末维护或线路，不是执行链。
- **复现**：P22-2。周六一条 rc=78 退出告警、2 分钟后 supervisor 已按设计重启 risk，仍返回 1；周六两段已恢复、共 3077 秒的断线，判"环境降级超限"，返回 1。对照 P22-2c：没有 supervisor 重启的周六 rc=78，T210 前后都应判异常。
- **处置（T210(b)，D105）**：
  - 非交易日的 rc=78 退出：10 分钟内有同组件的 supervisor 重启行，就记为记录类；没有，照旧判异常。
  - 1800 秒上限只用于交易日。
  - 所有日子的次数和秒数照常输出。
  - **交易日一律不变**：rc=78 判异常，超过 1800 秒判失败。

### O22-3 [High] main 的 CI 红：根目录脚本含本机绝对路径

- `deploy-consolidated.ps1`、`install-supervisor.ps1`、`supervisor-wrapper.cmd` 里共 15 处本机绝对路径（用户目录和工作区编号），P22-3 复现，CI 的 hygiene 闸门失败。
- 处置（D106）：
  - 主会话在**本机自己的克隆里**执行 `git rm --cached`（本地文件保留），加进 `.gitignore`，推送前跑卫生测试。
  - 需要留档的脚本，改成用占位符的脱敏副本入库。
  - 装一个本地 pre-push 钩子，推送前自动跑卫生测试。
  - 不改写历史（D84）。
- 审核线不代修：审核线一推删除，主会话下次拉取时 git 会删掉它本地的同名文件，而 11-22 的部署可能要用到这些文件。

### O22-4 [High] supervisor 在 Windows 上拉起的进程过不了自己的身份校验

- **事实**：
  - `live_supervisor.py` 的 `launch()` 用 `creationflags=CREATE_NO_WINDOW`，新进程会带一个 `conhost.exe` 子进程。
  - `verified_tree()` 要求树上每个后代都通过 `_identity()`（Python 解释器、参数逐项相符），`conhost.exe` 必然不过，报 `process script/arguments mismatch`。
- **复现**：P22-4。无 conhost 时校验通过；加一个 conhost 子进程，报错原文与 11-17 演练 A 相同。所以 11-17 的"`--risk-config` 与 `--config` 参数名不匹配"是误诊。
- **影响**：部署树里的 supervisor 在这台机器上一次也没能成功补起进程。现在靠树外 `host.py`（把 creationflags 改成 0，并让子进程继承一个隐藏控制台）运行。
- **处置（D102）**：
  - 本窗口接受 `host.py` 作为运维级补丁，条件是：
    - 脱敏副本入库；
    - 生产文件的 sha256 写进部署记录；
    - 11-22 之前做独立审核；
    - runbook §6.3 写明现在的实际安装方式。
  - A5 之后做树内修复（T208），然后撤掉 `host.py`。

### O22-5 [High] 没有可用的 supervisor 就进了窗口，主会话缺位两天

- 第二十一轮增补 §2 第 8 步把"supervisor 健康 + 两项演练"列为烧机和起算的前提。11-17 演练 A 失败后，supervisor 被停用、记为"非阻塞"，烧机照常开始。

## 4. 专题：两条基线有没有优化空间？策略是不是太少？

### 4.1 两条基线是什么

- B1（MaCrossATR M15，902610）和 B2（BuyHold H1，902501）都是**执行链试件**，代码里写明"只用于执行口径对账，不进策略库"（D30）。
- 它们在 A5 里的任务是产生证据：
  - B1 换手高，提供开仓、反手、成交归因、止损和止盈样本（正式检查要求 SL、TP 各至少一笔，只能来自 B1）；
  - B2 持有不动，提供"持仓期间零调仓"、心跳、对账、日报这些最干净的样本。
- 按这个任务衡量，两条现在的参数是够用的。

### 4.2 为什么不按盈亏去优化它们

1. **10 天的 Demo 盈亏说明不了任何事。** t 值约等于年化夏普 × √年数。10 个交易日约 0.04 年：
   - 年化夏普 1.0 的好策略，t 只有 0.2 左右；
   - 要 t 达到 1.645，同样的策略也要约 2.7 年数据。
   - 所以 Demo 盈亏只能用来对账，判断不了好坏。
2. **同类策略本项目已经测过。** 与 B1 同周期、同品种范围的标定样品，毛利与成本之比都没过 3 倍门槛（`docs/research/gates-calibration-2026-10-25.md`）：

   | 标定样品 | 品种 / 周期 | 毛利 ÷ 成本 |
   | --- | --- | --- |
   | H004 亚洲盘区间突破 | 欧元、黄金 M15 | 0.57 |
   | H005 均值回归（带趋势过滤） | 黄金 M15 | 2.30 |
   | H002 唐奇安趋势突破 | 黄金 H1（黄金腿） | 0.38 |

   在这家经纪商的成本下，日内黄金策略基本不赚钱，换参数改变不了这个结论。
3. **调参本身就是多重检验。** 每多试一组参数，台账里的 N 就增加，所有候选的 DSR 门槛都会抬高。不记账去试，就是数据挖掘。
4. **窗口内冻结。** 配置的 sha256 写在部署记录里，改一个参数就得重新部署、窗口重来。

### 4.3 真正"少"的是什么

1. **执行链只在一个品种上验证过。** 两条基线都是 XAUUSD。下一批研究候选要交易的品种和方式都没有被执行链跑过：
   - F3：货币对在伦敦定盘前后定时进出；
   - F1：黄金、欧元、纳指、比特币等 4–6 个品种的日频或周频调仓。

   没跑过的环节包括：
   - 外汇和指数的合约规格；
   - 按伦敦时间（含夏令时）定时进出；
   - 多品种同时下单时，按整个账户汇总的风控；
   - 周末也交易的品种（BTCUSD）。

   Demo 免隔夜费，所以隔夜费本来就验证不了，只能按快照记录成本漂移。
2. **研究漏斗里没有过闸门的候选。**
   - 登记过的候选：
     - H 线 C001–C005：一个撤回，四个只作历史复现（其中两个并入 D79 组合族）；
     - P 线 C101–C106 全部放弃；
     - P-Daily 等数据。
   - 合计十多个候选，没有一个满足 D76 的四条（`docs/research/candidate-triage-2026-11-13.md`）。
