## 3. 三处自报偏离裁定

### (a) test_t110_deadline.py 三处 `*a` → `*a, **k` —— 成立

三处（:36、:90、:131）均为子进程源码字符串里的 `class Fake` 的 `initialize` 方法签名，
改动仅加 `**k`（生产代码现在以 `initialize(path, timeout=ms)` 调用，不收 kwargs 会
TypeError）。返回值（True）与行为零改动；三处测试的**断言全部不在改动行**（断言在
subprocess 外层：rc=75、gateway-stall.json、journal pending/unknown 序列等，diff 证实
未触碰）。且 `stuck(*a, **k)` 替换分支本就收 kwargs。这是假模块对真实调用形态的签名
保真，非测试放宽。

### (b) test_t141_disconnect.py `_down_terminal` 的 terminal_info_value 由对象改 None —— 成立（按真实包形态建模正确）

- **真实包行为**：MetaTrader5 包约定所有 API 失败统一返回 None 并由 `last_error()`
  给原因；终端进程不在/IPC 未建立时 `terminal_info()` 返回 None（-10004 "No IPC
  connection" 一类）。规格 §2.1.1 自己的分支树（"返回 None（IPC 不通，例如终端进程
  不在）"）与探针 FakeMT5（ipc=False → None）同一建模。**真实包在终端进程不在时返回
  的是 None，不是 connected=False 的对象**——实现者方向正确。
- **改动前该对象本来就是死配置**：旧代码 `_attempt_reconnect` 先
  `_ensure_initialized()`，而 `_down_terminal` 同时设 `initialize_result=False`，
  initialize 直接失败抛 NotConnectedError——`terminal_info_value`（connected=False
  对象）在旧路径上**从未被读**。
- **改动后仍未被这 4 个用例消费**：4 个用例（退避节奏 :118、成功重置 :155、窗口内
  不砸 :180、call 恢复 :198）都不 `connect()`，`_initialized` 恒 False 直到
  `initialize_result=True`；`_ready_or_raise` 的 `not self._initialized` 短路（or 左
  边为真不求 `_terminal_ok()`），`_attempt_reconnect` 的探活在 `if self._initialized:`
  门内也不执行。FakeMT5.initialize 成功时自会恢复 connected=True 对象
  （fakes.py:78-83 `initialize_restores_connection`）。故 4 个用例的执行路径与断言
  （initialize 计数 1..7、5/10/30/60 节奏、恢复语义）前后**逐位不变**——103 passed 里
  它们全绿即证。
- **改动的真实价值是语义卫生**：若保留 connected=False 对象，未来任何走
  `_initialized=True` 探活路径的场景会落入 T201 新分支"等待终端自行重连"（零
  initialize），使这组按 initialize 计数断言的测试全部失效；None 钉死了"终端进程
  不在 → initialize 重建"的建模。非语义漂移，反而修正了原建模的形态错误。新形态
  （在线+服务器断）由 test_t201_reconnect_fix.py ①②专职覆盖，无覆盖缺口。

### (c) 配置上界条件生效（`init_upper_ms >= 1000` 才检查上界）—— 成立

- **理由核实**：T110 期限测试构造 `GatewayConfig(query_timeout_s=0.15,

## 4. 生产语义深查

### (a) connected=False 抛 NotConnectedError 后调用方行为与恢复链 —— 闭环成立

- 调用方消费（T141 既有架构，本提交未改）：risk_process.py:321 `except
  NotConnectedError` → `_handle_disconnect`（:267-292）→ `watch.note_failure`（15
  分钟 DisconnectWatch 计时）→ 降级轮（文件级检查照常、角色心跳照写）→ `reconnect()`
  （gateway.py:45-48 透传 MT5Connection.reconnect，未到点立即返回不阻塞轮询）。
  live_reconcile.py:240-259 同构；live_runner.py:951/992 走 blocked_broker_unavailable
  降级（断线轮心跳照写、journal 落 rejected 终态不留未决项）。
- **恢复链闭环**：服务器自愈 → terminal_info().connected=True → 因为 T201 保持了
  `_initialized=True`（②的"保持不变"），下一次任何调用 `_ready_or_raise`：
  `_initialized` 真 + `_terminal_ok()` 真 → **无需 initialize、无需重建 IPC**，直接
  正常执行；新加的 elif（connection.py:303-307）顺手清退避。风控/对账的
  `watch.note_ok()` 段内恢复告警+清零（monitor.DisconnectWatch，测试
  test_t141_disconnect_watch_expiry_reset_and_marker 钉死）。test_t201 测试②后半段
  （退避窗口内普通调用即通过并清退避）正是这条链的网关侧钉子。**若按旧代码调了
  initialize，66 秒挂死在恢复前就把进程带走了——这正是 11-10 全灭的机理；修复后
  "等终端自愈"与"进程活着等到自愈"构成完整因果闭环。**

### (b) 慢终端首连（connect → initialize with timeout）—— 有界失败，不再撞期限

- MetaTrader5 包所有调用失败**返回 None/False 而非抛异常**（`last_error()` 取原因）
  ——这是该包的基本约定，`_ensure_initialized` 的 `if not ok` 分支自 T110 时代即按
  此建模（connection.py:217-219 先于本提交存在）。MT5 侧 `timeout=15000` 到点 →
  initialize 返回 False → `_initialized=False` → `NotConnectedError("MT5 终端初始化
  失败：…")`，启动方按启动失败处理（supervisor 重启），原因清晰。
- **期限算术**：15s（MT5 侧）< 30s（T110 query_timeout_s）→ `future.result` 不会
  超时 → 不触发 `_fatal_timeout` → **不会 rc=75 三进程连锁**。最坏路径（initialize
  顶满 15s + `_terminal_ok` 一次探活 + 两次 `last_error`）仍远低于 30s。对比：修复前
  缺省 60s > 30s，实测挂 66s（MT5 60s 超时 + 进程内开销），第 30 秒 `os._exit(75)`。
  根因（P19-1 机理）就此消除。
- `initialize` 返回 False 的路径 `_initialized` 已置假（:218），与 IPC 不通路径状态
  一致，下轮到点重走 initialize——T141 退避节奏兜底，15 分钟总容忍由 DisconnectWatch
  （rc=78）把关。

### (c) `_ready_or_raise` 新增退避重置分支 —— 无循环风险

- elif（:303-307）仅在 `self._initialized` **且** `_terminal_ok()` 探活成功（IPC 通 +
  服务器通，最健康态）时执行，动作是两个清零赋值，零新增 MT5 调用。
- "探活成功但 initialize 状态坏死"的假想态不存在：`_initialized=True` 而 IPC 实际断
  → 探活返回 None → `_terminal_ok()` False → 走 if 分支 → 到点 `_attempt_reconnect`
  → 探活 None → 置假 → initialize 重建（恢复路径）；`_initialized=False` →
  `not self._initialized` 先短路，elif 根本不可达。elif 挂在 if/else 的 else 上，
  结构上排除了半坏态。
- 行为差异仅一处且是改善：退避窗口内服务器恢复时，下一次普通调用立即通过并清退避
  （原需等 `reconnect()` 到点），恢复延迟从最长一个退避周期缩到一次调用。

### (d) 附带说明：`_initialized=False` 链路上探活被跳过（规格分支树的不完备处）

规格 §2.1.1 字面是"`_attempt_reconnect()` 先调 `terminal_info()`"；实现把这一步放在
`if self._initialized:` 门内。差异场景：`_initialized=False` 且 IPC 已通、服务器未连
（例如终端进程重启后 IPC 恢复但服务器还没连上）时，实现每退避周期调一次 initialize
（有界 15s；IPC 通时真实包快速返回 True，对已建立 IPC 重复 initialize 幂等），而规格
字面是"不调 initialize、保持不变"。**严格照规格字面在该链路反而有死角**：
"connected 为真视为成功"只重置退避、不恢复 `_initialized=True`，则 `_initialized=False`
+ 服务器已恢复时永远回不到就绪态。实现用状态门选择"已知坏 → 直接重建"是两个权衡中
较安全者；且该链路每次尝试有 15s MT5 timeout + 30s T110 双保险，不存在撞期限（修复
目标不受影响）。主链路（`_initialized=True` 的运行中断线，11-10 实际形态）完全按规格
字面执行。记 §6 Low-1，不阻塞。
