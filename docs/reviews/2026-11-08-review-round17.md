## 3. 实盘与运维

**O17-1 [High] supervisor 自动重启不留证据，正式窗口的 A5 机械检查会因此失败**

- `scripts/demo_check.py::resolve_formal_window` 要求锚点之后 `ops-restarts.jsonl` 的每一行都绑定前、后两份 instances 副本（路径 + sha256）。runbook §4.1 写的是同一条要求。
- `scripts/live_supervisor.py::supervise` 重启时直接覆盖 `instances.json`，不留副本；仓库里也没有生成正式窗口描述符的工具，描述符只能手工拼装。
- 结果：夜间发生一次自动重启而没人当场复制文件，"重启前"的状态就丢了。再来一次重启，"第一次重启后"的状态也丢了。窗口检查会返回 2（证据不完整），A5 无从谈起。
- 修复（T180）：
  - supervisor 在覆盖前、写入后各留一份副本，并把两份副本的路径与 sha256 写进同一条 `ops-restarts.jsonl` 记录；
  - 部署时自动留存锚点所需的 manifest、launcher、instances 副本；
  - 新增描述符生成器；
  - 用"部署后发生两次自动重启"的合成场景端到端验证，正式检查应返回 3（机械满足）。
- 留存失败时写告警，但不阻止重启。

**O17-2 [High] 交易终端被每日数据任务占用，时间恰在纽约盘中（P17-5）**

- `scripts/setup_scheduled_tasks.ps1` 按本机时间（UTC+8）每天运行四个任务，换成 UTC 正好落在 XAUUSD 盘中，四个都连同一终端：

  | 任务 | 本机时间 | UTC |
  | --- | --- | --- |
  | snapshot_specs | 00:05 | 16:05 |
  | refresh_bars | 00:10 | 16:10 |
  | refresh_ticks | 00:15 | 16:15 |
  | live_daily_report | 00:20 | 16:20 |

- 11-05 取证的时间线（`docs/ops/exit-forensics-2026-11-05.md` §1）：
  - refresh_ticks 的 `copy_ticks_range` 起于 16:15:11.9；
  - 风控的 `terminal_info` 起于 16:15:19.0；
  - 两者在 16:15:49 先后被 30 秒期限硬停。
- 取证文档写的是"终端整体无响应"。更具体的解释是：一天的 tick 下载（按 7 天分块，多个品种）占住了终端的 API，其他进程的调用跟着挂起。
  - 这个解释与 11-05 的时间完全吻合。
  - 11-06 11:22 那次不在任务时间内，原因另查（O17-5）。
- 风险：窗口内这四个任务每天都会在盘中再来一次，可能每天杀掉一个实盘进程；tick 任务自己也会被期限杀掉，数据刷新可能不完整。
- 修复（T182，部署前）：
  - 把 specs、bars、ticks 三个任务改到周六运行；
  - 日报改到 XAUUSD 换日休市窗口内运行，或改成只读文件、不连终端；
  - runbook §7 增加一条：窗口内不得在交易终端上运行任何临时脚本或研究下载；
  - 中期做法：装第二个 MT5 终端（独立数据目录），专供数据与研究，交易终端只服务三个实盘进程。

**O17-3 [Medium] 下单前取不到账户 = 请求确定未发出，却被当成"回报未知"（P17-3）**

- `MT5Connection.trade_send` 在 `account_info` 为空时抛 `DataUnavailableError`，此时 `order_send` 尚未调用。
- 执行器的下单路径只单独处理 `TradeRejectedError` 与 `NotConnectedError`，`DataUnavailableError` 落进兜底分支：journal 记 unknown 后重抛，运行器经 guarded_main 退出并写 halt。
- 修复（T183）：trade_send 对"发送前检查失败"抛一个专用异常（可作为 `NotConnectedError` 的子类），走 T141 的 blocked 路径。保险丝与账号不符（`LiveTradingBlockedError`）仍然退出。

**O17-4 [Medium] 风控约 50 秒取不到账户就 halt，要等人工解除（P17-4）**

- T142 把 `DataUnavailableError` 列为可恢复异常，计入 5 轮上限。风控 `--interval 10`，所以约 50 秒后以 rc=79 退出，并写 `owner=risk` 的 halt。supervisor 只清自己写的 halt。
- 在终端时有抖动、执行方又不是全天在线的情况下，这会在夜里把交易停到第二天。
- 修复（T184）：账户取数失败改按时间窗计（建议 5 分钟，配置项），文件占用与锁超时仍按 5 轮计。halt 语义不变，对账进程同样处理。

**O17-5 [Medium] 取证看错了目录：终端日志在数据目录的 `logs\`，不在 `MQL5\Logs\`**

- 取证文档把"MT5 终端自身 `MQL5/Logs` 不存在"列为证据缺口。但 MT5 的平台日志（连接、授权、交易）写在终端数据目录的 `Logs\yyyymmdd.log`；`MQL5\Logs` 放的是 EA 日志，本项目不跑 EA，自然没有。
- 五次 −6（authorization failed）窗口、11-05 14:45 的 10021、11-06 11:22 的挂起，根因证据很可能都在前者。
- 修复（T185）：取这些日期的平台日志、Windows 事件日志与任务计划器历史，以及 11-06 11:22 前后各会话的命令记录。原件含账号与服务器名，只留本地，公开脱敏摘要。

**O17-6 [Low] 两腿决策中途断线时，journal 会把已执行的平仓腿记成"请求未发出"**

- 场景：反向决策先平后开，平仓腿成交后断线，开仓腿抛 `NotConnectedError`。此时决策仍在 `_journal_unsent` 里（`_journal_sent` 只在整份回报返回后调用），journal 落 `rejected / not_connected：请求未发出`。
- 断线期间查不到净持仓时，意图退回 `net_before`，与券商不一致，由对账进程暂停。处理是 fail-closed 的，但证据写错了。
- 修复：任一腿已发出时记 unknown，交给重启核对；不必赶在本次部署前完成。

**O17-7 [Low] 两份只读核对用了两套 PID**

- 11-07 主会话记的是 3408/13308/6160，调度会话记的是 5892/1632/5536，两边都说进程连续运行。
- 这符合 Windows venv 的结构：instances.json 登记的是 venv 启动器，心跳里是解释器子进程。
- 日检模板应同时写两套 PID、父子关系与启动时刻，否则无法从记录判断是否发生过未登记的重启。

**O17-8 [Low] 其他**

- supervisor 重启没有退避：终端持续挂起时，每个监督周期都会重启一次。
- `gateway-stall.json` 只有一个槽位，11-05 风控那份已被 11-06 覆盖。

### 4.2 发现

**H17-1 [High] D1 事件窗的时间口径：MT5 数据段上错一天（P17-1）**

- 研究序列 `h-input-v1` 是 FRED 段接 MT5 段，两段对"00:00 这一行"的含义不同：
  - **FRED 段**（close-only）：日期 t 的行，开 = 收 = t 日官方收盘；
  - **MT5 段**（OHLC）：日期 t 的行在 UTC 00:00 开盘，开盘价约等于 t−1 日收盘。
- `fomc_calendar_events` 把入场、出场都取在交易日 00:00；`event_returns` 取该时刻那根 bar 的开盘价。在 FRED 段上这正好是登记窗"锚日收 → 公告日收"；在 MT5 段上，量到的是锚日开盘 → 公告日开盘，约等于锚日自己的收益。
- 探针：合成序列在公告日收对收涨 3%、锚日持平。FRED 段量到 +3.05%；MT5 段量到 +0.00%；引擎 A 跑 T151 事件窗策略，MT5 段那笔也是 +0.00%。
- 影响：
  - R3 主检验不受影响；
  - R3 报告 §6 的 MT5 段 34 个事件（−2.9bp）与"2021 年后合计 −3.9bp"量错了窗口，作废；
  - T151 的策略类如果在 MT5 数据上交易，会持有公告日前一天；
  - 以后任何跨接缝或只用 MT5 段的 D1 事件研究（例如 N2）都会受影响；
  - T151 的对账测试用的是 OHLC 合成数据，引擎与研究口径错得一样，测试照样通过。
- 修复（T187）：事件窗按"价格时点"定义（某日收盘），研究序列在接缝两侧采用同一种 bar 口径，并加接缝测试。要求：
  - 两段上量到的收益都等于登记窗收益；
  - R3 主检验段 213 个事件的收益前后逐位相同（等价锚点）；
  - 改动后 data_sha256 与指纹随之变化，后续运行计为新试验。

**H17-2 [Medium] verdict_code_sha 覆盖不全（P17-2）**

- 指纹只由三部分组成：`validation/events.py`、整份 `bt.py`、日历工件。事件模式 V3 判决还调用了：
  - `validation/lookahead.py`：`run_g0`，G0 是判定项；
  - `validation/robustness.py`：`ScaledCosts`，成本 ×1.5 否决项；
  - `validation/gates.py`：`evaluate_v3` 与两个否决项函数；
  - `costs/*` 的计算代码：试验身份里的 `cost_model_version` 只描述配置，不描述代码。
- 指纹文档说"任何裁决路径改动必变指纹，反之不漏"，这一点不成立。
- 另一面是过宽：整份 bt.py（约 5,900 行）任何改动都会生成新试验。
- 修复（T188）：干净检出时，取判决路径所在子树（`src/mt5quant`、`src/mt5data`、`scripts/bt.py`）的 git tree 哈希作指纹，同时记录提交号。旧行保持不变。

**H17-3 [Medium] 随机化检验仍慢（T152 未做）**：run6 用了约 5.5 小时，同形合成数据上不到 2 分钟。`event_returns` 对每个事件现查点差模型（`spread_p90`），并逐个包装成本对象，是最可疑的热点。应先在真实输入上 cProfile，改成每次运行预计算一次，并做逐位等价测试。只有再开事件模式轮次时才需要做。

**H17-4 [Low] 留痕**：R3 关闭报告的三段重算（`t150-closure-segments.*`）与离线复现仍只在本地 `.superpowers/`。这些不含敏感信息，按 D72 应进 `docs/`。

## 7. 方案：策略方向与 D68 修订

**D68 的问题。**

- 按前向数据达到 50% 检验力所需年数 ≈ (1.96 / 年化夏普)²：

  | 年化夏普 | 所需年数 |
  | --- | --- |
  | 0.5 | 15 年 |
  | 0.7 | 8 年 |
  | 0.9 | 4.7 年 |

- "≤ 5 年"等价于要求年化夏普 ≥ 0.88（P17-6），几乎没有现实的候选能进 Demo。
- 但 Demo 不动用真钱，它要验证的是实现保真：实盘成交、成本与回测是否一致，以及运维是否可靠，不是确认 edge。

**D76（建议，待用户确认）。** 进入 Demo 路线需要同时满足：

- 历史检验按预注册通过，且在发表后效应量下的历史检验力 ≥ 50%；
- 最近十年（或发表后）分段的点估计扣除成本后为正；
- 有前向监测计划：逐笔回测与实盘对账、成本漂移，以及明确的停止条件。

前向检验力年数保留为必须披露的数字，但不再作为 Demo 门槛；任何涉及真钱的讨论仍以它为准（真实账户目前本来就禁止）。D76 确认之前，D68 继续有效。

**研究方向（D79，建议，待用户确认）。**

- 单一事件类候选（每年约 8 次）先暂停。下一个候选从"每年独立观测多"的组合类设计里选，例如多品种日频跨资产趋势组合。
- 这类效应文献多、样本长，可参考 Moskowitz、Ooi 与 Pedersen（2012），以及 Hurst、Ooi 与 Pedersen（2017）。
- 先按 T154、T155 做可行性与检验力评估，不算收益。前提是品种池（D60 已同意评估阶段）、早年数据与隔夜费状态（U5）可得。
- 范围控制按 D71：研究线同时只推进这一个。
