## 结论

**H 线**

1. **R1 对 C002 的"falsified"结论作废（H15-1、H15-2，High）**。R1 的两次运行都没有检验 C002 登记的假设：
   - 关卡 V3 事件分支的方向是命令行常量 `--event-side`（缺省 long），C002 登记的方向由 USTEC 当月涨跌决定，代码里根本没有信号品种；
   - bar 级 B7 用的是 EURUSD 自己的当月涨跌（"同序列近似"）；
   - 检验只读了 MT5 研究库（46 个事件，约 3.8 年），而开轮依据的预筛检验力按 HistData + MT5 合并的 18.72 年计算。

   R1 的那次运行实际上是"每月末定盘前一小时按固定方向持有 EURUSD"（命令行没给方向时为做多；实际取值记在台账 run 450 的 `event_side` 字段，T113 核对）。它照样计入试验次数，但不能作为 C002 的结论。C002 以新版本在 R2 重检，主检验只用没被看过的 HistData 段（D58）。
2. **实盘进程会卡死或静默退出，而代码没有任何自救与留痕（H15-3，High）**。网关调用没有超时，风控循环只捕获一种异常，进程 stdout 重定向到文件时是块缓冲，没有 faulthandler，也没有外部看门狗；风控进程不发布自己的心跳，它死了以后运行器仍可开仓。阶段 F 第 3 日风控进程冻结 13 分钟以上，11-01（周日）三个进程在 05:03 UTC 退出、停摆约 8 小时，原因至今不明。PR #5 没有覆盖这一点。
3. **阶段 F 的 10 个交易日需要重新起算（H15-4）**。窗口内改过三次实盘代码，两次停摆无法解释；日志把周六、周日记成交易日 4、5（XAUUSD M15 周末不交易）。合并 PR #5 与卡死防护后，在冻结版本上重新跑连续 10 个交易日，此前的天数作为磨合期记录（D57）。
4. **PR #5（H2-01/02/03）批准合并**，附部署条件（§1.3）。
5. 第十四轮的四项冻结条件、T86 接线、T94 年数切段、T20 换日实测、swap-free 确认均核对无误（§1.1）。

**P 线**

1. **T75 概率模式标定（P 线批准点）：方法不批准，P2-09 方法门保持关闭**。三个方法都没有通过：月内置换与季度块在成簇负对照上误报 11% 与 8%；cluster-permutation-v1 未达两段终局标准。并且它在结构上不可用（P15-1）：簇按真实日与对照日的并集单链聚合，日子越多簇越少——每组 600 个随机日就只剩 2 个簇，1,200 个日只剩 1 个簇。这正是 v4 报告里 n ≥ 2000 检出率为 0 的原因。不再做单链簇置换，也不做 v4 §6 计划的月块自助批次（D59）。
2. **候选全部不可检验的终局归档，批准**。另外指出一个审核侧的设计错误：S1 整数关口给 XAUUSD 定的是每 50 美元，按价格比例约为 EURUSD 每 0.0050 的 9 倍粗，按 H1 ATR 计约 3 倍，触发自然稀少（§2.2 P15-3）。
3. **P 线在现有形态下同时被成本和样本量卡死（P15-2）**。登记 Δp = 2 个百分点，对应 ΔEV = 0.06R；而 1R = 1×ATR(H1) 时，保守成本 XAUUSD 0.021–0.031R、EURUSD 0.056–0.062R，3 倍成本处处超过 ΔEV。下一步不再打磨检验方法，先做一次**只数触发、只算成本**的可行性筛查：换更大的括号或 H4、按价格比例定网格、视 D60 决定扩品种。有可行的设计族，才重启方法工作；没有就让 P 线休眠，保留基础设施（交接文档 T121）。
4. **PR #6 批准合并**。P2-10 覆盖研究预注册扎实，RED 结论成立：D41 的期望值下界在格间异质、同日成簇时不保守。P2 运行前必须先升级估计器（D61）。研究门禁四态只是读侧汇总，可以接受。

### 1.2 发现

**H15-1 [High] R1 的事件检验用的是常量方向，C002 的登记假设从未被检验**

- `scripts/bt.py:1519` 取 `side = ctx["side"]`，`:1530` 写 `side_fn = (lambda event: side)`，`ctx["side"]` 来自 `:4116` 的 `args.event_side`，`:4992` 定义 `--event-side` 只能取 long/short，缺省 long。
- C002 与 H101 登记的规则是"USTEC 当月上涨 → 做多 EURUSD，下跌 → 做空"。事件分支拿不到信号品种的数据，也没有按事件取方向的接口。
- bar 级 B7（`b7_monthend_hedge_rebalance.py:30`）明文写着信号与成交"同为传入序列"，即用 EURUSD 自己的当月涨跌。
- 结果：run 449（screen）与 run 450（gate）检验的都不是 C002。R1 报告的"不通过（p = 0.979，成本否决未过）"描述的是固定方向这条规则（缺省做多，以 run 450 记录的 `event_side` 为准），`falsified` 登记不成立。
- 复现：探针 H15-1。合成数据上，按登记方向的均值是 +9.85bp，bt 的事件分支只能算出固定做多的 +0.61bp。
- 处置（D58）：
  1. 更正记录。台账追加更正、R1 报告加更正节、蓝图 §5 改写；run 449/450 照常计入 N（D33），不删除。
  2. 事件模式支持信号驱动的方向。候选与轮次声明 `signal_symbol`、`side_rule`，事件分支按规则逐事件取方向，随机化零分布里的随机事件用同一规则取方向；静态方向只在轮次登记为静态时允许，不一致拒绝运行。
  3. 信号品种与成交品种不同的 bar 级策略，研究运行一律拒绝"同序列近似"。
- 落地见交接文档 T112–T114。

**H15-2 [High] 预筛与检验用的数据覆盖不一致**

- C002 预筛的检验力按 EURUSD H1 合并覆盖 18.72 年计算（MT5 2021-05 起，加 HistData 2007-01 起各段，见 `C002.precheck.json` 的 `checks.power.coverage_segments`），单次检验力 64%。
- H 线的 `cmd_screen`（`bt.py:3621`）与 `cmd_gate`（`:4143`）都用 `load_series` 读 MT5 研究库；`merged_research_series` 只在 P 线入口使用（`_prob_load_bars` 等）。R1 实际只有 46 个事件，按隐含夏普 0.49 估算检验力约 25%。
- 这是系统性缺口：开轮条件按一种数据计算，检验用另一种数据。
- 处置：
  - H 线研究运行在候选预筛计入外部数据时读合并序列，遵守 X-03 的边界契约，外部数据段的点差按 ×1.5 绑定；
  - 运行前（只看时间戳、不看收益）比较实际覆盖与预筛覆盖，实际覆盖不足预筛的 90% 就拒绝运行，或者按实际覆盖重算检验力，低于 50% 判 waiting_data；
  - 实际覆盖写进台账和关卡报告。
- 复现：探针 H15-2。

**H15-3 [High] 实盘进程卡死与静默退出没有防护**

- 代码事实（探针 H15-3）：
  - `src/mt5gw`、`src/mt5live` 和三个进程脚本里，没有调用超时、卡死看门狗或 faulthandler；
  - `scripts/risk_process.py` 的循环只捕获 `DataUnavailableError`，其他异常会让风控进程直接退出；
  - `demo_run.ps1:585` 把 stdout 与 stderr 重定向到文件，Python 此时是块缓冲，日志"冻结"可能只是没刷盘，也可能是真卡住，现在无法区分；
  - 风控进程不写自己的心跳，运行器也不检查它是否活着——风控进程死了，日亏全平与心跳监视都停了，运行器仍可开仓。
- 阶段 F 事实：
  - 10-30 13:13 起风控进程日志不再推进，心跳超时演练没有触发停机；
  - 11-01 05:03 UTC 三个进程全部退出，13:25 才重启，期间 `.err` 日志、Windows 事件日志、MT5 终端日志都没有被调取。
- PR #5 只在 runbook §6.1 建议加外部新鲜度探测，没有实现。
- 处置（交接文档 T110）：
  - 网关调用加期限，超时写日志后以专用退出码退出，下单超时按"执行未知"处理，由 PR #5 的 journal 恢复；
  - 风控进程写自己的心跳，运行器的闸门在风控心跳过期时拒绝新开仓（平仓不受限）；
  - 进程用无缓冲输出启动，加 faulthandler、顶层异常日志和退出标记；
  - 外部监督任务（Windows 计划任务）检查三个进程的存活与心跳，风控失联时写 halt，进程死了或卡住就重启，每次动作写运维记录；
  - 调取两次事故时段的日志做取证。

### 1.3 PR #5 审核结论：批准合并，附条件

### 2.2 发现

**P15-1 [High] cluster-permutation-v1 在结构上不可用，不应作为后续方向**

- `src/mt5quant/validation/prob_mode.py:288` 把真实日与对照日合并后，相邻间隔不超过 10 个日历日就归为同一簇（单链）。触发日越密，簇就越少、越大。
- 探针 P15-1：6 年工作日里每组随机取 100、300、600、1,200 日，簇数依次为 83、32、2、1，最大簇占比 6%、9%、58%、100%。v4 报告里 n ≥ 2000 时只剩约 31 个簇，最大簇占约 55%，检出率为 0，与此一致。
- 结论：即便 w3 的置信上界过了线，这个方法在 P1 需要的样本量上也没法用——样本越多，检验越退化。
- v4 §6 计划的下一批"月块自助"在固定月边界处同样会切开跨月簇，有放回重抽还有偏差，同样不推荐（D59）。

**P15-2 [High] 现有设计族同时被成本和样本量卡死**

- **成本**：括号是止盈 2R、止损 1R 时，ΔEV = 3 × Δp；Δp = 0.02 时 ΔEV = 0.06R。按 T97 实测，保守档成本 XAUUSD 0.021–0.031R、EURUSD 0.056–0.062R，3 倍成本全部超过 0.06R。即使 Δp 翻倍，EURUSD 仍然不过。
- **样本量**：最多的 C104 S1:A3 只有 1,333 个触发日，要求是 > 7,424。
- 这两条都由设计决定：1R = 1×ATR(H1) 时，点差占 R 的比例太高；按日期聚合时，加品种也不会按名义倍数增加独立日。
- 继续打磨 P1 的检验方法解决不了这两个问题。下一步是只数触发、只算成本的可行性筛查（T121），先写定判定标准，再在少数几个预先固定的设计族上计算：
  - 括号尺度（止损 2×ATR(H1) 或改用 H4）；
  - 按价格比例与市场惯例定网格；
  - 视 D60 决定是否扩品种。

  通过的设计族才重启方法标定（T122）；没有通过的，P 线进入休眠，基础设施保留。

**P15-3 [Medium，审核侧责任] S1 网格的品种间尺度不一致**

- 蓝图 §2.1 照搬"以 00 和 50 结尾"，给 XAUUSD 定的是每 50 美元：发现段金价约 1,050–1,550 美元，间距约为价格的 3.8%；EURUSD 每 0.0050 约为 0.43%，两者相差约 9 倍。
- 按 H1 ATR 计，XAUUSD 的间距约 16 个 ATR，EURUSD 约 5 个，相差约 3 倍。
- Osler（2003）的证据针对外汇报价的末两位；把它换算成黄金的美元整数并没有文献依据。
- 这是蓝图（审核侧）的错误，不是执行侧的问题。后续新版本必须先写定网格原则（按价格比例与市场惯例，各品种口径一致），在计数之前登记，不得按计数结果挑网格。

**P15-4 [Medium] T75 报告批准点的结论**

见 §2.3。

**P15-5 [Medium] P2-10 覆盖研究（PR #6）的结论与限制**

- RED 结论成立，主因有三：
  - 收缩目标（同一动作的共享经验基准）相对每格真值有偏，大样本时偏差主导；
  - 同日成簇按行数计算标准误；
  - 全赢、全输时标准误为 0。
- 限制：覆盖率的大小取决于模拟里设定的格间异质性（Dirichlet 浓度 40）。估计器 v2 要在多种异质性设定下验证，不能只在一种生成器上过关。
- 处置（D61）：P2（T92）运行之前，D41 的下界估计器必须升级为 v2 并通过预注册验证；现在不改代码，P2 本来就到不了。

**P15-6 [Low] P2 接线未逐行复核**

T73B、T104/T105 的 P2 接线（逐窗拟合、OOS 起点、白名单、Brier 否决）本轮没有逐行读。T92 启动前需要一次专项复核（T125）。

**P15-7 [Info] 简化模拟没有复现成簇误报（P15-2 探针，INFO）**

- 在小时级随机游走加成簇同向触发的简化模拟里：
  - 1,500 日（约 250 个触发日，400 次）："全局对照 + 月内置换"误报率 6.0%，"局部配对 + 按月符号翻转"5.2%，检出率相近；
  - 6,000 日（约 1,000 个触发日，150 次）：两者误报率分别为 6.0% 与 8.7%（次数少，置信区间宽），Δp = 0.05 时检出率 84% 与 72%。
- 这个模拟没有复现 T75 在真实池上 11% 的成簇误报，说明那个误报主要来自真实行情的状态结构（趋势、波动聚集），不是窗口重叠本身；局部配对设计在这里也没有显出优势，大样本时误报还偏高。
- 推论：任何新方法都必须在 T75 的真实池负对照上实测，不能用简化模拟替代，也不能预设赢家。局部配对设计（对照取自触发前后几日、同小时、同方向、同 ATR 档）理论上能抵消慢变状态，可作为 T122 的首选候选，但它在大样本下的误报必须作为 T122 的重点验收项，以实测为准。

## 3. 流程与治理

1. **单会话（D56）**：本地会话同时负责 H 线、P 线与实盘运维，是唯一写 main 的执行方。外部会话（全局审核、PR 复审）只产出报告或 PR。
   - 每个提交只属于一条线，提交说明带前缀 `[H]`、`[P]`、`[S]`（共用底座）、`[OPS]`；
   - 并行子代理必须各用独立 worktree，只由主会话合并（第十四轮 L7 教训）。
2. **批准归属**：两条线的批准点都交本审核会话（D49 的细化）。批准结论写在 `docs/reviews/` 的审核报告里；轮次文件的 `approved_by` 由审核会话在批准提交中填写，执行会话不得填写。
3. **research-allowlist**：该工作流对所有 PR 套用研究角色白名单，管理员路径的 PR 必然失败；管理员改动按设计应当直推 main。不要为了让 PR 变绿去削弱它。要求的状态检查与分支保护属用户操作（Issue #4 第 2 项）。
4. **规模控制**：
   - `scripts/bt.py` 已有 5,028 行，`candidates.py`、`ledger.py` 各近 2,000 行；
   - 本轮起不再新增框架性模块，修复优先在原位做小改动；
   - 同时进行中的任务不超过一个实盘任务加一个研究任务。
