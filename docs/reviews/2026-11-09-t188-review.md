## 3. tree 哈希语义与跨平台一致性（评审重点 2）

- **类型差异与组合**：`HEAD:src/mt5quant`、`HEAD:src/mt5data` 解析为 tree 对象 ID，`HEAD:scripts/bt.py` 解析为 blob 对象 ID（`git cat-file -t` 亲验）。组合=sha256(`"verdict-code-v2"` + 固定元组顺序的 `"\n{rel}:{objectid}"`×3 + `"\ncalendar:{component}"`)：路径标签把 tree 命名空间与 blob 命名空间的 40-hex ID 显式区分（防跨类型拼接混淆），固定顺序防排列歧义，域标签防跨版本误等。结构健全。
- **跨平台/行尾**：git 对象 ID 在提交时按内容寻址写入对象库，`rev-parse` 只读 ID、完全不接触工作树——同一提交在任何平台/任何 autocrlf/任何检出形态（甚至无检出）下 ID 逐位相同。旧 D66 的 `_sha256_lf_normalized` 读工作树字节再 CRLF→LF 归一，其目的（Windows CRLF 检出==Linux LF 检出）被"工作树不再是输入"彻底包含。**删除安全**：grep 全仓确认该函数无其他调用者（gates.toml 的 `gates_sha256`（gates.py:219）是另一函数，本提交未触碰）。语义上指纹改为"精确已提交内容"的身份——同逻辑内容若在不同历史以不同行尾提交则是不同 tree=不同试验，这正是判决代码身份应有的精确语义。
- **D66→v2 组成变更的记账**：域分隔符升 verdict-code-v2；生产台账本无 verdict_code_sha 列（§0），故生产不存在 v1 值需要保留；测试/合成库中旧行 v1 值不动。首个事件模式运行自然计新试验（与 D74 data_sha256 变更同语义），提交说明明写。

## 4. 提交号不进指纹/去重的裁量（评审重点 3）

**核验**：指纹输入=三 objectid+日历，无 commit（bt.py:1538–1543）；runs 八元组去重键 `_dedup_keys/_dedup_n/round_n_dedup`（ledger.py:1842–1915）与 `_dedup_trial_sharpes`（bt.py:1296–1300）均只含 verdict_code_sha；reservation trial_key 的 extra 只并入 verdict_code_sha（bt.py:5158–5159）；`LockboxTrial` 字段只有 verdict_code_sha（bt.py:5455–5459，gates.py:819–828 仅 docstring 更新）。verdict_commit 仅进 runs 行、V3 details、报告文本。

**机械复证**：合成仓库空提交（--allow-empty）→ 指纹逐位不变、commit 变化、identity["commit"]==新 HEAD。

**裁量正当性**：试验身份的语义是"什么代码在判决"，不是"哪个历史标签指向它"。同树异提交（rebase/amend/空提交/revert 回同一子树内容）执行逐位相同的判决逻辑——计为不同试验会虚增 N（多重性控制的对立面）；verdict_commit 保留溯源（谁、在哪提交上判的）。反例情形（verdict 路径 A→B→A′，A′≡A：与 A 期试验去重合并）恰是 desired：同判决逻辑不重复计数。**判定：裁量正当**，且与 strategy_sha/data_sha256 的"内容身份"口径同构。

## 9. 残留风险

- **F-1 [Low] git 异常类型未归一到优雅拒绝**：cmd_gate 只捕 RuntimeError；git 缺失（FileNotFoundError）/超时（TimeoutExpired，10s 上限）以 traceback 退出。仍 fail-closed（入账前、rc≠0、零 runs），仅报错形态与"✗ …"不一致。建议下次触碰时 except (OSError, subprocess.TimeoutExpired) 一并转优雅退 1。
- **F-2 [Low] 脏树判定=porcelain 口径（clean-filter 等价，非字节等价）**：本机 core.autocrlf=true 下，把 HEAD 为 LF 的工作树文件重写为 CRLF，porcelain 判"干净"（实测放行）——指纹描述 HEAD、执行字节与 HEAD 差行尾。Python 源码语义对行尾不敏感（唯一例外是跨行字符串字面量内嵌换行），风险趋于零；且这与预检 T170 完全同口径（分层一致，非新引入）。skip-worktree/assume-unchanged 标记同样可欺瞒 porcelain（git 自身语义），同归此类。
- **F-3 [Info] bt.py 整文件 blob 仍全敏感**：~5,900 行任一改动（含与判决无关的 bar 级分支）仍触发新试验——H17-2"过宽"一面只收窄到 D75 路径表边界，bt.py 内部过宽是 D75 逐字指定所固有（计划如此，非遗漏）；后续把事件分支拆模块（蓝图已有此意向）时自然消解。
- **F-4 [Info] 探针"按常量动态判定"名实差**：实现为对指纹函数源码文本的子串匹配（`p in fp_src`），非读取 `bt._VERDICT_CODE_PATHS` 值。修复前后均正确（两侧亲测），但未来重构改常量字符串会静默退化探针判定。建议改为 hasattr 时直接读常量、无则回退源码扫描。
- **F-5 [Info] 测试与真实仓库三路径干净度耦合**：T151（test_verdict_code_sha_is_trial_identity 后段、CLI 断言 `_verdict_code_sha()` 无 repo_root）与 T188 CLI 测试隐含要求运行测试的检出在三判决路径上干净——CI 干净检出无虞；本地脏树开发时这些测试以 RuntimeError 失败（fail-loud，方向正确，但属新的环境耦合，值得知悉）。
- **F-6 [Info] 已声明后续项**：（a）verdict-code-v2 基线变更后，t112 类漂移守卫 pin 若引用判决身份需重钉（实现方提交说明已声明"下一提交"处理，本提交未触及该 pin，CI workflow 无指纹类 pin 复核过）；（b）生产台账下次可写打开将连续触发 T151+T188 两块迁移（双 rechain，终态一致幂等），之后须 --accept-rechain 重锚——运维动作别漏。
